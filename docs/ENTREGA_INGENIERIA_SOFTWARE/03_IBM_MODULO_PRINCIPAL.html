1. Alcance del módulo principal

El módulo principal de SIGEL es el ciclo comercial de Travel BQTO: publicar destinos, consultar la oferta, reservar cupos y asignar asientos. En las plantillas IBM se identifica como M1. Agrupa RF-04, RF-12, RF-13 y RF-14.

Los diagramas UML que acompañan este módulo son:

  • Secuencia y actividad (carriles): PATRON_RESERVA_PORTAL, RESERVA_CREAR, RESERVA_ASIENTO.
  • Consulta pública de destinos: RF-13 / M1-U2.

M1-U1 — Crear destino

IdentificadorM1-U1
NombreCrear destino turístico
Actor principalAdministrador
Actores secundariosSistema SIGEL, base de datos
PropósitoRegistrar un destino de la oferta de Travel BQTO con precio, descripción e imágenes.
ResumenEl administrador abre el catálogo, carga los datos del destino y, si la validación es correcta, el sistema lo persiste y lo deja consultable en el panel y en el portal público.
TipoEsencial / primario
ReferenciasRF-04; RNF-06, RNF-12; Diagrama A y C
PrecondicionesSesión autenticada con permiso de crear destinos.
Postcondiciones de éxitoExiste un destino activo. Queda registro en bitácora (módulo destinos, acción insertar).
Postcondiciones de falloNo se persiste el destino. El actor ve el motivo (validación, permiso o error de almacenamiento).

Flujo principal

  1. El administrador abre Destinos y elige crear.
  2. La interfaz solicita nombre, descripción, precio base e imágenes.
  3. El administrador completa el formulario y confirma.
  4. La interfaz valida campos visibles (nombre, precio, formato de imagen).
  5. El sistema verifica token y permiso.
  6. El modelo persiste el destino y, si hay fotos, las asocia a la galería.
  7. Se registra la bitácora.
  8. La interfaz muestra confirmación y el destino aparece en el listado y en el catálogo público.

Flujos alternos

  • A1 Datos incompletos o inválidos: la interfaz o la API rechazan (400/422). No hay persistencia. Vuelve al paso 2.
  • A2 Imagen no admitida: se informa el tipo permitido. El destino puede guardarse sin esa foto o el actor corrige el archivo.

Flujos de excepción

  • E1 Sin sesión o sin permiso: 401/403. No se crea el destino.
  • E2 Fallo de persistencia: mensaje genérico. El administrador reintenta.

Reglas de negocio

  • El precio base es obligatorio y mayor que cero.
  • Las imágenes de galería se almacenan en formato web adecuado (WebP).

M1-U2 — Consultar destinos

IdentificadorM1-U2
NombreConsultar destinos
Actor principalVisitante (portal) o Administrador (panel)
Actores secundariosSistema SIGEL
PropósitoMostrar la oferta turística publicada y el detalle de un destino.
ResumenEl visitante consulta el catálogo sin autenticarse. El administrador consulta el mismo maestro con datos de gestión.
TipoEsencial / primario
ReferenciasRF-04, RF-13; RNF-14, RNF-16; Diagrama C
PrecondicionesPortal: ninguna. Panel: sesión con permiso de lectura de destinos.
Postcondiciones de éxitoSe muestra el listado o el detalle. No se modifica el maestro.
Postcondiciones de falloMensaje de catálogo vacío o destino inexistente.

Flujo principal

  1. El actor abre el portal (inicio / catálogo) o Destinos en el panel.
  2. El sistema solicita los destinos activos al catálogo o al maestro.
  3. La interfaz presenta tarjetas o tabla (nombre, precio, imagen de portada).
  4. El actor selecciona un destino.
  5. El sistema devuelve el detalle (descripción, galería, viajes asociados si aplica).

Flujos alternos

  • A1 Catálogo vacío: se informa que aún no hay destinos publicados. Es el estado inicial de la base limpia.
  • A2 Filtro o búsqueda sin resultados: listado vacío con criterio visible.

Flujos de excepción

  • E1 Destino inexistente o anulado: 404. El portal no muestra el detalle.
  • E2 Servicio no disponible: mensaje de error de consulta. No se inventan datos.

Reglas de negocio

  • El visitante no requiere cuenta para consultar.
  • Solo destinos no anulados son visibles en el portal público.

M1-U3 — Modificar destino

IdentificadorM1-U3
NombreModificar destino
Actor principalAdministrador
Actores secundariosSistema SIGEL
PropósitoActualizar datos o galería de un destino existente.
ResumenEl administrador abre el destino, edita campos o imágenes y confirma. El sistema valida, persiste y audita.
TipoEsencial / primario
ReferenciasRF-04; RNF-04, RNF-06; Diagrama A
PrecondicionesSesión con permiso de editar destinos. El destino existe y no está anulado.
Postcondiciones de éxitoLos cambios son visibles en panel y portal. Bitácora con acción de actualización.
Postcondiciones de falloSe conservan los datos anteriores.

Flujo principal

  1. El administrador selecciona el destino y abre edición.
  2. El sistema carga los datos actuales.
  3. El actor modifica nombre, descripción, precio o galería.
  4. Confirma el guardado.
  5. El sistema valida, actualiza y registra bitácora.
  6. La interfaz confirma el cambio.

Flujos alternos y excepciones

  • A1 Validación fallida: no se guarda. Se muestran los campos a corregir.
  • E1 Destino anulado o inexistente: 404. No hay edición.
  • E2 Sin permiso: 403.

M1-U4 — Anular destino

IdentificadorM1-U4
NombreAnular destino
Actor principalAdministrador
Actores secundariosSistema SIGEL
PropósitoRetirar un destino de la oferta sin borrar su historia.
ResumenEl administrador solicita la anulación. Si no hay viajes o reservas dependientes activos, el sistema aplica eliminación lógica.
TipoEsencial / secundario
ReferenciasRF-04; RNF-05; Diagrama A
PrecondicionesSesión con permiso de anular destinos. El destino existe y está activo.
Postcondiciones de éxitoEl destino deja de publicarse. Queda marca de anulación y bitácora.
Postcondiciones de falloEl destino permanece activo. Se informa la dependencia que lo impide.

Flujo principal

  1. El administrador selecciona anular en el destino.
  2. La interfaz pide confirmación.
  3. El sistema verifica dependencias (viajes o reservas asociadas).
  4. Si no hay bloqueo, aplica anulación lógica.
  5. Registra bitácora y confirma.

Flujos alternos y excepciones

  • A1 El actor cancela la confirmación: no hay cambio.
  • A2 Hay viajes o reservas dependientes: se rechaza la anulación. El destino sigue publicado.
  • E1 Sin permiso: 403.

Reglas de negocio

  • No se elimina físicamente el registro.
  • Un destino con operación vigente no se retira del maestro.

M1-U5 — Registrar reserva

IdentificadorM1-U5
NombreRegistrar reserva con viajeros
Actor principalAdministrador o Cliente
Actores secundariosSistema SIGEL, bitácora
PropósitoAsegurar cupo en un viaje para un titular y sus acompañantes, sin sobreventa.
ResumenEl actor elige viaje, titular, viajeros, puntos de recogida y, si aplica, asientos. El sistema valida cupo y unicidad de asiento, persiste la reserva y audita. Diagrama de secuencia y actividad: RESERVA_CREAR / PATRON_RESERVA_PORTAL.
TipoEsencial / primario
ReferenciasRF-12; RNF-08, RNF-15; Diagramas B y C
PrecondicionesViaje publicado con cupo. Cada viajero existe como cliente. Cliente: sesión de rol Cliente y perfil. Administrador: permiso de crear reservas.
Postcondiciones de éxitoExiste la reserva (código visible). Se debitó cupo. Viajeros en reserva_clientes. Bitácora del módulo reservas.
Postcondiciones de falloNo hay reserva. Cupo y asientos permanecen como estaban.

Flujo principal

  1. El actor abre la reserva (panel o portal) y selecciona el viaje.
  2. Indica el titular y agrega acompañantes. Cada persona es un cliente.
  3. Asigna punto de recogida por viajero cuando corresponda.
  4. Consulta asientos disponibles (M1-U10) y elige asientos (M1-U8) si el viaje los usa.
  5. La interfaz valida el formulario y envía la solicitud.
  6. El sistema verifica sesión, rol o permiso.
  7. El modelo consulta y bloquea viaje, cupo y asientos.
  8. Si las reglas se cumplen, guarda reserva, viajeros y asientos.
  9. Registra bitácora y devuelve el identificador (RES-id).
  10. La interfaz muestra confirmación al actor.

Flujos alternos

  • A1 Datos de interfaz inválidos: no se envía o se rechaza 400/422. El actor corrige.
  • A2 Acompañante no registrado: se crea primero como cliente (RF-11) y se retoma el paso 2.
  • A3 Sin asientos en este paso: la reserva puede quedar con asiento pendiente y asignarse después (M1-U8).

Flujos de excepción

  • E1 Sesión inválida o rol insuficiente: 401/403.
  • E2 Viaje o cliente inexistente: 404.
  • E3 Cupo agotado o asiento ocupado: 409. Se informa el motivo. No hay sobreventa.

Reglas de negocio

  • Una reserva pertenece a un cliente titular y a un viaje.
  • Los viajeros no duplican nombre ni documento: se enlazan por cliente_id.
  • Un asiento vigente no puede repetirse en el mismo viaje.
  • Dos solicitudes simultáneas sobre el último cupo: una confirma y la otra recibe 409.

M1-U6 — Consultar reservas

IdentificadorM1-U6
NombreConsultar reservas
Actor principalAdministrador o Cliente
Actores secundariosSistema SIGEL
PropósitoListar y abrir el detalle de reservas según el alcance del rol.
ResumenEl administrador ve el maestro de reservas. El cliente ve solo las suyas en el portal (mis reservas).
TipoEsencial / primario
ReferenciasRF-12, RF-14; RNF-01, RNF-02; Diagramas B y C
PrecondicionesSesión válida. Administrador: permiso de lectura. Cliente: perfil de cliente asociado.
Postcondiciones de éxitoSe muestra listado y/o detalle. No se altera la reserva.
Postcondiciones de falloListado vacío o acceso denegado.

Flujo principal

  1. El actor abre Reservas (panel) o Mis reservas (portal).
  2. El sistema filtra según rol: todas las vigentes para el administrador; solo las del titular para el cliente.
  3. La interfaz muestra código, viaje, estado y saldo cuando aplica.
  4. El actor abre una reserva y ve viajeros, asientos, recogida y pagos asociados.

Flujos alternos y excepciones

  • A1 Sin reservas: estado vacío con indicación de crear o esperar publicación de viajes.
  • E1 El cliente intenta una reserva ajena: 403. No se revela el detalle.
  • E2 Reserva inexistente: 404.

Reglas de negocio

  • El portal nunca lista reservas de otros clientes.
  • Los estados visibles son de negocio (pendiente, confirmada, abonada, cancelada), no códigos internos de base de datos.

M1-U7 — Gestionar reserva en el portal

IdentificadorM1-U7
NombreGestionar reserva desde el portal del cliente
Actor principalCliente
Actores secundariosSistema SIGEL, administrador (conciliación de pagos, M2)
PropósitoPermitir al pasajero continuar su reserva: consultar saldo, reportar pago, mantener recogida y, si aplica, reseñar el viaje.
ResumenCon sesión de cliente, la persona opera solo sus reservas. Este caso cubre el autoservicio del RF-14 ligado a M1.
TipoEsencial / primario
ReferenciasRF-14; RNF-01, RNF-14, RNF-15; Diagrama C
PrecondicionesCliente autenticado con al menos una reserva propia, o un viaje disponible para reservar.
Postcondiciones de éxitoQueda registrada la acción del portal (reserva, reporte de pago o actualización de recogida) en el alcance del cliente.
Postcondiciones de falloNo hay cambio. Mensaje comprensible en español.

Flujo principal

  1. El cliente inicia sesión y entra al portal.
  2. Consulta el tablero y sus reservas (M1-U6).
  3. Elige una acción: completar reserva, ver saldo, reportar pago o editar punto de recogida.
  4. El sistema valida titularidad y datos.
  5. Persiste el cambio permitido al rol Cliente.
  6. Muestra confirmación. Si reportó pago, el estado queda en validación (módulo M2).

Flujos alternos y excepciones

  • A1 No hay viajes publicados: el portal lo indica. No se fuerza una reserva vacía.
  • A2 Reserva no elegible para reseña: la opción no se habilita.
  • E1 Token vencido: se pide nuevo inicio de sesión.
  • E2 Intento de actuar sobre reserva ajena: 403.

Reglas de negocio

  • El cliente no concilia pagos: solo reporta. La aprobación es administrativa (M2).
  • El flujo crítico de reserva se completa en no más de cuatro clics desde el inicio del rol (RNF-16).

M1-U8 — Asignar asiento

IdentificadorM1-U8
NombreAsignar asiento a un viajero
Actor principalAdministrador (panel) o Cliente (durante la reserva)
Actores secundariosSistema SIGEL
PropósitoOcupar un asiento libre del viaje para un viajero de la reserva, sin duplicar ocupación.
ResumenEl actor elige reserva, viajero y asiento. El sistema bloquea el asiento del viaje y lo vincula. Diagrama: RESERVA_ASIENTO.
TipoEsencial / primario
ReferenciasRF-01, RF-12; RNF-08; Diagramas B y C
PrecondicionesReserva existente. Viajero vinculado. Unidad del viaje con mapa de asientos. Permiso de editar reservas o titularidad en portal.
Postcondiciones de éxitoEl viajero tiene asiento. El asiento queda vigente para ese viaje. Bitácora.
Postcondiciones de falloEl asiento no cambia de dueño.

Flujo principal

  1. El actor abre la reserva y selecciona el viajero.
  2. Consulta el mapa (M1-U10) y elige un asiento libre.
  3. Confirma la asignación.
  4. El sistema verifica sesión y permiso o titularidad.
  5. El modelo bloquea reserva, viajero y asiento del viaje.
  6. Si el asiento está libre, lo asigna y audita.
  7. La interfaz actualiza el mapa y el detalle del viajero.

Flujos alternos y excepciones

  • A1 El viajero ya tenía asiento: se sustituye solo si el nuevo está libre y las reglas lo permiten; el anterior se libera.
  • E1 Asiento ocupado por otra reserva: 409. El mapa se refresca.
  • E2 Viajero o reserva inválidos: 404.
  • E3 Sin permiso: 403.

Reglas de negocio

  • Índice único de asiento vigente por viaje: no hay dos ocupaciones activas del mismo asiento.
  • La anulación de la reserva (M1-U9) libera los asientos.

M1-U9 — Anular reserva

IdentificadorM1-U9
NombreAnular reserva
Actor principalAdministrador
Actores secundariosSistema SIGEL
PropósitoCancelar una reserva y devolver cupo y asientos al viaje.
ResumenEl administrador confirma la anulación. El sistema marca la reserva como cancelada, libera asientos vigentes y registra bitácora.
TipoEsencial / secundario
ReferenciasRF-12; RNF-04, RNF-05; Diagrama B
PrecondicionesReserva existente y no cancelada. Permiso de anular o editar reservas.
Postcondiciones de éxitoEstado cancelada. Asientos liberados. Cupo disponible incrementado según reglas. Bitácora.
Postcondiciones de falloLa reserva conserva su estado anterior.

Flujo principal

  1. El administrador abre la reserva y elige anular.
  2. La interfaz pide confirmación.
  3. El sistema valida permiso y estado actual.
  4. Marca la reserva cancelada y libera asientos vigentes.
  5. Registra bitácora y confirma.

Flujos alternos y excepciones

  • A1 El actor cancela el diálogo: no hay cambio.
  • A2 Reserva ya cancelada: se informa. No se opera de nuevo.
  • E1 Sin permiso: 403.

Reglas de negocio

  • La anulación no borra el histórico de viajeros ni de pagos ya registrados.
  • Los asientos vuelven a estar libres para M1-U8 y M1-U10.

M1-U10 — Consultar disponibilidad de asientos

IdentificadorM1-U10
NombreConsultar mapa y disponibilidad de asientos
Actor principalAdministrador o Cliente
Actores secundariosSistema SIGEL
PropósitoMostrar qué asientos del viaje están libres u ocupados antes de asignar.
ResumenEl actor abre el mapa del viaje. El sistema combina la plantilla de la unidad con las ocupaciones vigentes y pinta el estado de cada asiento.
TipoEsencial / primario
ReferenciasRF-01, RF-16 (flota como apoyo); RNF-08; Diagramas B y C
PrecondicionesViaje existente con unidad y asientos configurados. Sesión según el canal (panel o portal en reserva).
Postcondiciones de éxitoEl actor ve el mapa actualizado. Esta consulta no ocupa asientos.
Postcondiciones de falloNo se muestra mapa. Se indica viaje o unidad sin asientos.

Flujo principal

  1. El actor abre la reserva o el viaje y solicita el mapa.
  2. El sistema obtiene la plantilla de asientos de la unidad y las ocupaciones vigentes del viaje.
  3. Devuelve cada asiento como libre u ocupado.
  4. La interfaz pinta el mapa. El actor puede continuar con M1-U8.

Flujos alternos y excepciones

  • A1 El viaje no tiene unidad o asientos: se informa que hay que configurar la flota (RF-16) antes de asignar.
  • E1 Viaje inexistente: 404.
  • E2 Sin permiso o sin titularidad: 401/403.

Reglas de negocio

  • La consulta no reserva. La ocupación efectiva ocurre en M1-U5 o M1-U8.
  • Un asiento ocupado no se ofrece como seleccionable.
